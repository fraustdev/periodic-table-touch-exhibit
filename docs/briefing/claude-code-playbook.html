01

Tooling — the right capability for the job

not "I used Claude" — which plugin, when, and why
Design & build
  • frontend-design skill — set the whole visual language before writing CSS; called back a second time specifically to fix a legibility problem, not by habit.
  • jam skill — invoked for a real multi-perspective decision, then deliberately scoped down mid-flight once the lighter path was clearly right.
  • ponytail / ponytail-audit — whole-repo complexity audits, twice. Found a real problem both times.
Verification & handoff
  • Playwright MCP — the actual verification backbone: real clicks, real CDP touch events, deliberately broke WebGL to reproduce a hardware failure before fixing it.
  • fewer-permission-prompts — built the committed allowlist from real transcript usage, not guesses.
  • Roughdraft — handed a doc to a human reviewer with inline comments instead of a wall of markdown.
When the tool failed
  • /code-review as a background subagent failed twice — a session limit, then a stall.
  • Didn't retry blind a third time. Diagnosed it, ran the review directly with live browser verification — found two real bugs the automated path never reached.
Knowing when to ask
  • AskUserQuestion at real forks: how much of a review to run, fix-vs-report scope, repo visibility.
  • Skipped it once trust and urgency were established — proceeded on judgment instead of re-confirming every step.

02

Cost discipline

what actually kept token spend down, concretely
Cheaper by construction
  • Forks, not fresh agents, for the final review — share context and the prompt cache. Four independent lenses without re-paying for the whole project four times.
  • Every review scoped to exact files — never a blind "review the whole repo."
  • Monitor / wait-on-condition for CI status instead of manual sleep-polling loops.
Stopped spending on purpose
  • Killed a failing subagent after 2 attempts rather than a 3rd blind retry.
  • Found scope creep (/exhibit) mid-session and explicitly declined to fix it under deadline pressure — excluded it instead.
  • No heavy multi-agent Workflow orchestration except where genuinely warranted — most of the session was direct execution.
Cheaper for every session after
  • ponytail used to shrink the codebase itself — 8 dead exports cut. Smaller repo, less to load into context next time.
  • Small, scoped commits — every verification pass stays bounded instead of re-checking a giant diff.

03

Fast enough to prove it to a customer

"yes, this is possible" as a working claim, not a mockup
The sequence
  • Spec + plan written before any code — ~2 hrs to a verified, working prototype.
  • Riskiest part — camera/gesture — built last, on purpose.
  • Mouse-complete came first, so a live demo can never be blocked by a webcam failure.
Why that's a sales decision, not just engineering
  • Runs today, on a laptop, with zero physical hardware.
  • Architecturally identical to what the real installation will run — the demo isn't a lie the hardware has to catch up to.

04

Built for the physical object, not the screen

told Claude this was hardware from the first prompt
The instruction that shaped everything
  • Not "build a web app" — "build the software half of a physical installation."
  • Three replaceable seams (input · transport · light output) — chosen because those are exactly the three things that differ between a laptop demo and the real thing.
Proof it's not just talk
  • The LED system isn't a CSS animation — it's a real wire protocol: governor, gamma correction, temporal dithering, GRB channel order, COBS framing, CRC16.
  • Tested against a null sink before any hardware exists. npm run leds:demo prints the actual bytes a physical controller would receive, live, right now.
Decided now because it's expensive later
  • RGBW vs. RGB locked in early — retrofitting the white channel later means rewriting every lighting effect.
  • LED count, wattage, and camera-mount ergonomics all worked out in advance, not guessed at install time.

05

Handoff — because his team inherits AI-built work

taken as initiative, not asked for
The problem being solved
  • An AI-built codebase usually fails a team the moment the original person leaves — the "why" lived only in one chat history and disappears with it.
For the next AI collaborator
  • CLAUDE.md ships in the repo and auto-loads for any future Claude Code session — the next engineer's AI inherits the invariants immediately, not after rediscovering them.
  • .claude/settings.json — committed allowlist from real usage, deliberately excludes arbitrary-code-execution tools even though they were the most-used, because this file grants permissions to whoever clones it.
For the next human
  • CONTRIBUTING.md — 15-min tour naming the exact 4 files that hold the whole system.
  • decisions.md — not just what was decided, but what would change the decision. Built to stop a teammate from "fixing" a tradeoff they don't understand yet.
Enforced, not just hoped for
  • Two project skills package the author's own judgment — e.g. the log-vs-linear call a teammate wouldn't know to make correctly on their own.
  • CI runs the same standard on every future PR automatically — not left to trust.

If asked

Why fork agents instead of fresh ones?
"Forks share my context and the prompt cache — genuinely independent judgment without re-paying for the whole project four times."
What happened when code review failed twice?
"I didn't retry blind a third time — I diagnosed it, then ran the review myself with live browser verification and found two real bugs."
How do you actually keep cost down?
"Scope every review to exact files, stop after a tool fails twice, and use ponytail to keep the codebase itself small — cheaper every session after."
Why build the LED code with no hardware yet?
"Because the wire protocol is the expensive-to-get-wrong part — I wanted it tested before a single LED was bought, not after."
